title: Auth Service Object

The `authService` object provides comprehensive authentication functionality for your Arkos application. While Arkos handles authentication automatically behind the scenes, you may need direct access to the authentication methods in your business logic.

## Accessing the Auth Service

The `authService` is automatically available in your Arkos application and can be imported directly:

```ts
import { authService } from "arkos/services";
```

For a guided, example-first walkthrough of calling these methods outside the router — in services, jobs, scripts and tests — see [Manual Usage](/docs/core-concepts/authentication/advanced/manual-usage).

<Callout type="warn">
On the following section you will various examples on how you can use the authService, you ain't restricted to those but also in the same time bear in mind that **Arkos** handles many of auth relate scenarios, such as authentication, authorization, password hashing, password checks and many others.
</Callout>

Before proceed reading this guide is highly encouragend to read the guide about how **Arkos** uses this under the hood so that you do not miss anything and try to reivent the wheel yourself, [Arkos Authentication Flow Guide](/docs/guides/validation/setup#authentication-endpoint-validation).

## API Reference

### JWT Token Management

#### `signJwtToken(id, expiresIn?, secret?)`

Signs a JWT token for a user.

**Parameters:**

- `id` (number | string): The unique identifier of the user
- `expiresIn` (optional): The expiration time for the token (defaults to JWT_EXPIRES_IN from environment)
- `secret` (optional): The secret key for signing (defaults to JWT_SECRET from environment)

**Returns:**

- A signed JWT token string

**Example:**

```ts
// In a custom middleware
export const beforeCreateOne = catchAsync(async (req, res, next) => {
  // Generate a token with custom expiration for special access
  const temporaryToken = authService.signJwtToken(req.user.id, "4h");
  req.body.temporaryAccessToken = temporaryToken;
  next();
});
```

#### `verifyJwtToken(token, secret?)`

Verifies the authenticity of a JWT token.

**Parameters:**

- `token` (string): The JWT token to verify
- `secret` (optional): The secret key to use for verification

**Returns:**

- Promise resolving to the decoded JWT payload (AuthJwtPayload)

**Throws:**

- Error if the token is invalid or expired

**Example:**

```ts
// A custom middleware for API key validation
export const validateApiKey = catchAsync(async (req, res, next) => {
  try {
    const apiKey = req.headers["x-api-key"] as string;
    const decoded = await authService.verifyJwtToken(apiKey);

    // Add custom authorization flags
    req.isApiRequest = true;
    req.apiClientId = decoded.id;
    next();
  } catch (err) {
    next(new AppError("Invalid API key", 401));
  }
});
```

#### `getJwtCookieOptions(req)`

Builds the cookie options used for the JWT access token cookie. It merges, in order of precedence, your Arkos configuration, environment variables, the request's own properties (for the `secure` flag) and sensible defaults.

**Parameters:**

- `req` (ArkosRequest): The request object, used to infer whether the connection is secure

**Returns:**

- A `CookieOptions` object with `expires`, `httpOnly`, `secure`, `sameSite` and `domain`

**Throws:**

- Error if `req` is not provided

**Example:**

```ts
// Manually set the access token cookie in a custom route
const token = authService.signJwtToken(req.user.id);
res.cookie(
  "arkos_access_token",
  token,
  authService.getJwtCookieOptions(req)
);
```

### Password Management

#### `isCorrectPassword(candidatePassword, userPassword)`

Compares a candidate password with the stored user password.

**Parameters:**

- `candidatePassword` (string): The password provided during login attempt
- `userPassword` (string): The hashed password stored in the database

**Returns:**

- Promise resolving to boolean (true if passwords match)

**Example:**

```ts
// Custom password validation for sensitive operations
export const beforeCreateOne = catchAsync(async (req, res, next) => {
  // Require password confirmation for critical operations
  if (!req.body.confirmPassword) {
    return next(new AppError("Please confirm your password", 400));
  }

  const isValid = await authService.isCorrectPassword(
    req.body.confirmPassword,
    req.user.password
  );

  if (!isValid) {
    return next(new AppError("Password confirmation failed", 401));
  }

  // Remove password from request body to prevent accidental exposure
  delete req.body.confirmPassword;
  next();
});
```

#### `hashPassword(password)`

Hashes a plain text password using bcrypt.

**Parameters:**

- `password` (string): The plain text password to hash

**Returns:**

- Promise resolving to the hashed password string

**Example:**

```ts
// In a custom user invitation flow
export const beforeCreateOne = catchAsync(async (req, res, next) => {
  // Generate a secure one-time password for invited users
  if (req.body.isInvitedUser) {
    const tempPassword = generateSecureRandomPassword();
    req.body.password = await authService.hashPassword(tempPassword);
    req.body.passwordResetRequired = true;

    // Store the plain password temporarily for email sending
    req.tempPassword = tempPassword;
  }

  next();
});
```

#### `isPasswordStrong(password)`

Checks if a password meets strength requirements.

**Parameters:**

- `password` (string): The password to check

**Returns:**

- boolean (true if the password meets strength criteria)

**Example:**

```ts
// Add custom password policies beyond default requirements
export const beforeUpdatePassword = catchAsync(async (req, res, next) => {
  const { newPassword } = req.body;

  // Or can use built-in validation through DTO or Schema
  if (!authService.isPasswordStrong(newPassword)) {
    return next(
      new AppError("Password doesn't meet security requirements", 400)
    );
  }

  // Add additional custom password policy checks
  if (newPassword.includes(req.user.username)) {
    return next(new AppError("Password cannot contain your username", 400));
  }

  next();
});
```

#### `isPasswordHashed(password)`

Checks whether a value already looks like a bcrypt hash. Arkos uses this internally before hashing a `password` field so that an already-hashed value is not hashed a second time.

**Parameters:**

- `password` (string): The value to test

**Returns:**

- boolean (true if the value is already a bcrypt hash)

**Example:**

```ts
// Avoid double-hashing when accepting pre-hashed imports
if (!authService.isPasswordHashed(req.body.password)) {
  req.body.password = await authService.hashPassword(req.body.password);
}
```

### User Authentication

#### `userChangedPasswordAfter(user, JWTTimestamp)`

Checks if a user changed their password after a JWT was issued.

**Parameters:**

- `user` (User): The user object containing the passwordChangedAt field
- `JWTTimestamp` (number): The timestamp when the JWT was issued

**Returns:**

- boolean (true if password was changed after JWT issuance)

**Example:**

```ts
//  A custom middleware for API integrations
export const validateLongTermToken = catchAsync(async (req, res, next) => {
  const integrationToken = req.headers["x-integration-token"];
  if (!integrationToken) return next();

  const decoded = await authService.verifyJwtToken(integrationToken);
  const user = await prisma.user.findUnique({ where: { id: decoded.id } });

  if (!user) {
    return next(new AppError("Integration user not found", 401));
  }

  // Check if password was changed, invalidating all tokens
  if (authService.userChangedPasswordAfter(user, decoded.iat)) {
    return next(
      new AppError(
        "Integration token expired due to password change",
        401
      )
    );
  }

  req.integrationUser = user;
  next();
});
```

#### `getAuthenticatedUser(req)`

Retrieves the authenticated user from a request.

**Parameters:**

- `req` (ArkosRequest): The request object

**Returns:**

- Promise resolving to the authenticated User object or null

**Throws:**

- AppError if token is invalid or user not found

**Example:**

```ts
// Custom conditional authentication based on route context
export const optionalAuthentication = catchAsync(async (req, res, next) => {
  try {
    // Try to authenticate but don't require it
    const user = await authService.getAuthenticatedUser(req);

    if (user) {
      req.user = user;
      req.isAuthenticated = true;
    } else {
      req.isAuthenticated = false;
    }

    // Content filtering logic based on authentication status
    if (!req.isAuthenticated) {
      req.query.isPublic = true;
    }

    next();
  } catch (err) {
    // Continue as unauthenticated rather than failing
    req.isAuthenticated = false;
    req.query.isPublic = true;
    next();
  }
});
```

#### `validateDecodedUser(decoded, action?)`

Loads the user referenced by a decoded JWT payload and validates that the account still exists and that the password has not changed since the token was issued. Used internally by `getAuthenticatedUser`, but exposed for custom token handling.

**Parameters:**

- `decoded` (AuthJwtPayload): The decoded JWT payload (must contain an `id`)
- `action` (optional, `"logout" | "default"`): Pass `"logout"` to skip the password-change check. Defaults to `"default"`

**Returns:**

- Promise resolving to the full `User` object

**Throws:**

- `AppError` (`UserNoLongerExists`) if the user no longer exists
- `AppError` (`PasswordChanged`) if the password changed after the token was issued and `action` is not `"logout"`

**Example:**

```ts
const decoded = await authService.verifyJwtToken(token);
const user = await authService.validateDecodedUser(decoded);
```

#### `authenticate`

Middleware function to authenticate the user based on the JWT token.

**Example:**

```ts
// A custom router with specialized access control
import { Router } from "express";
import { authService } from "arkos/services";
import { catchAsync } from "arkos/error-handler";

const router = Router();

// Only allow access during business hours
const businessHoursOnly = catchAsync(async (req, res, next) => {
  const now = new Date();
  const hour = now.getHours();

  if (hour < 9 || hour >= 17) {
    return next(
      new AppError(
        "This API is only available during business hours",
        403
      )
    );
  }

  next();
});

// Route with custom authentication chain
router.get(
  "/api/business-data",
  authService.authenticate,
  businessHoursOnly,
  (req, res) => {
    res.status(200).json({
      status: "success",
      data: {
        message: "Welcome to the business API",
        user: req.user,
      },
    });
  }
);

export default router;
```

### Auth Flow Methods

> Available from 1.8.0-rc

These methods power the built-in `/auth` endpoints and can be overridden through `RouteHook<"auth">.service` by extending `AuthService`. The argument order is fixed by the controller; see [Authentication Service Override](/docs/core-concepts/components/service-override#authentication-service-override) for the full contract.

Except for `logout`, each method returns the result the controller sends back, and none of them ever include the `password` field.

#### `getMe(userId, queryOptions?)`

Retrieves the authenticated user by id without the password field.

**Parameters:**

- `userId` (User["id"]): The id of the authenticated user
- `queryOptions` (optional, GetMeOptions): Prisma query options (`select`, `include`, etc.)

**Returns:**

- Promise resolving to the sanitized user or `null`

**Example:**

```ts
import { AuthService as ArkosAuthService } from "arkos/services";
import type { User } from "@prisma/client";

// Override to attach a computed field
class AuthService extends ArkosAuthService {
  async getMe(
    userId: User["id"],
    queryOptions?: Parameters<ArkosAuthService["getMe"]>[1]
  ) {
    const user = await super.getMe(userId, queryOptions);
    return user && { ...user, isProfileComplete: !!user.bio };
  }
}
```

#### `updateMe(userId, data, queryOptions?)`

Updates the authenticated user and returns the sanitized result. Updating the `password` field through this method is rejected — use `updatePassword` instead.

**Parameters:**

- `userId` (User["id"]): The id of the authenticated user
- `data` (UpdateMeDto): The fields to update
- `queryOptions` (optional, UpdateMeOptions): Prisma query options

**Returns:**

- Promise resolving to the sanitized updated user

**Throws:**

- `BadRequestError` (`InvalidFieldPassword`) if `data` contains a `password` field

#### `signup(data, queryOptions?)`

Creates a new user account and returns it without the password field. The password is hashed automatically by the underlying `BaseService`.

**Parameters:**

- `data` (SignupDto): The user data
- `queryOptions` (optional, SignupOptions): Prisma query options

**Returns:**

- Promise resolving to the sanitized created user

#### `deleteMe(userId, queryOptions?)`

Marks the authenticated user's account as self-deleted by setting `deletedSelfAccountAt`, and returns the sanitized user.

**Parameters:**

- `userId` (User["id"]): The id of the authenticated user
- `queryOptions` (optional, DeleteMeOptions): Prisma query options

**Returns:**

- Promise resolving to the sanitized updated user

#### `login(input, queryOptions?)`

Authenticates a user from a username field and password.

The username field is inferred from the username key present in `input` (the only key besides `password`), so `{ email, password }` queries the `email` field. Pass `usernameField` explicitly for nested paths such as `"profile.nickname"` — whose key is `nickname` — since the inference only sees the key. When no username key is present, it falls back to `authentication.login.allowedUsernames[0] || "username"`. The password is always loaded for the comparison and never returned.

**Parameters:**

- `input` (LoginInput): `{ password, [username]: value, usernameField? }`
- `queryOptions` (optional, LoginOptions): Prisma query options

**Returns:**

- Promise resolving to `{ user, accessToken }`

**Throws:**

- `BadRequestError` (`MissingCredentialFields`) if the username or password is missing
- `BadRequestError` (`IncorrectCredentials`) if no user matches or the password is wrong

#### `updatePassword(userId, input)`

Updates the user's password after validating the current one, and returns a fresh access token.

**Parameters:**

- `userId` (User["id"]): The id of the authenticated user
- `input` (UpdatePasswordInput): `{ currentPassword, newPassword }`

**Returns:**

- Promise resolving to `{ accessToken }`

**Throws:**

- `AppError` (`SameCurrentAndNewPassword`) if either password is missing
- `AppError` (404) if the user does not exist or is inactive/deleted
- `AppError` (`IncorrentCurrentPassword`) if the current password is wrong
- `BadRequestError` (`PasswordDoesNotMeetRequirements`) if the new password is too weak

#### `logout(userId, accessToken)`

Runs on logout. It is a no-op by default and exists so you can override it for token revocation, server-side session invalidation or audit logging. Arkos clears the access-token cookie after this method runs.

**Parameters:**

- `userId` (User["id"]): The id of the authenticated user
- `accessToken` (string): The access token being invalidated

**Returns:**

- Promise resolving to `void`

**Example:**

```ts
import { AuthService as ArkosAuthService } from "arkos/services";
import type { User } from "@prisma/client";

class AuthService extends ArkosAuthService {
  async logout(userId: User["id"], accessToken: string) {
    await revokedTokens.add(accessToken);
  }
}
```

### Access Control Handlers

#### `handleAccessControl(action, modelName, accessControlConfig)`

<Callout type="warn" title="Deprecated">
Use [`authorize`](#authorizeaction-resource-rule) instead. This method will be removed in v2.0.
</Callout>

Middleware function to handle access control based on user roles and permissions.

**Parameters:**

- `action` (AccessAction): The action being performed (e.g., Create, Update, Delete, View or custom actions)
- `modelName` (string): The model name that the action is being performed on
- `accessControlConfig` (AccessControlConfig): The configuration object for authentication and access control

**Returns:**

- Middleware function that checks if the user has permission

**Example:**

```ts
// Implementing department-specific access control
import { authService } from "arkos/services";
import { catchAsync } from "arkos/error-handler";

const generateDepartmentReport = catchAsync(async (req, res, next) => {
  // Report generation logic
  const report = await generateReport(req.params.departmentId);
  res.status(200).json({ status: "success", data: report });
});

// Apply contextual access control with department check
const protectedReportAccess = [
  authService.authenticate,
  authService.handleAccessControl(
    "View", // action
    "report", // resource name
    ["Admin", "DepartmentHead"]
    // restricts only to those roles in static rbac
  ),
  // Additional custom department ownership check
  catchAsync(async (req, res, next) => {
    if (
      req.user.role !== "Admin" &&
      req.user.departmentId !== parseInt(req.params.departmentId)
    ) {
      return next(
        new AppError(
          "You can only access your own department reports",
          403
        )
      );
    }
    next();
  }),
  generateDepartmentReport,
];

export { protectedReportAccess };
```

#### `handleAuthenticationControl(action, authenticationControlConfig)`

<Callout type="warn" title="Deprecated">
Use [`authenticate`](#authenticate) instead. This method will be removed in v2.0.
</Callout>

Handles authentication control by checking the configuration.

**Parameters:**

- `action` (AccessAction): The action being performed
- `authenticationControlConfig` (AuthenticationControlConfig | undefined): The authentication configuration object

**Returns:**

- Middleware function that checks if authentication is required

**Example:**

```ts
// Implementing tiered access for different content levels
import { authService } from "arkos/services";
import { catchAsync } from "arkos/error-handler";

const getContentData = catchAsync(async (req, res, next) => {
  let contentLevel = "basic";

  // If authenticated, provide premium content
  if (req.isAuthenticated) {
    contentLevel = "premium";
  }

  const data = await getContentByLevel(contentLevel);
  res.status(200).json({ status: "success", data });
});

// Apply optional authentication for tiered content
const tieredContentAccess = [
  authService.handleAuthenticationControl(
    "View",
    { View: false } // Not required but supported
  ),
  // Custom middleware to track authentication status
  catchAsync(async (req, res, next) => {
    req.isAuthenticated = !!req.user;
    next();
  }),
  getContentData,
];

export { tieredContentAccess };
```

#### `authorize(action, resource, rule?)`

> Available from 1.6.0-beta

Middleware to authorize the authenticated user for a given action on a resource. It runs the `authentication.hooks.authorize` pipeline and is the current replacement for `handleAccessControl`.

**Parameters:**

- `action` (AccessAction): The action being performed (e.g., `"View"`, `"Create"`, `"Delete"`, or a custom action)
- `resource` (string): The resource being accessed, in kebabCase (e.g., `"product"`, `"cart-item"`)
- `rule` (optional): The access control rule for this action. Accepts a role list, a wildcard (`"*"`), or a `DetailedAccessControlRule`

**Returns:**

- Middleware function that checks whether the user is authorized

**Example:**

```ts
router.delete(
  "/products/:id",
  authService.authenticate,
  authService.authorize("Delete", "product", ["admin"]),
  handler
);
```

#### `permission(action, resource, accessControl?)`

Creates a permission checker for a specific action and resource. The returned function takes a user and resolves to a boolean.

This method is intended to be called during application initialization — call it at module scope to build a named permission set. Permission checkers created this way are also discovered by Arkos and exposed through the `GET /api/auth-actions` endpoint.

**Parameters:**

- `action` (string): The action to check permission for (e.g., `"View"`, `"Create"`, `"Delete"`)
- `resource` (string): The resource being accessed, in kebabCase (e.g., `"user"`, `"cart-item"`)
- `accessControl` (optional, AccessControlConfig): Access control rules required in static mode. Automatically loaded for known modules such as Prisma models, `auth` and `file-upload`

**Returns:**

- A function `(user) => Promise<boolean>` indicating whether the user has permission

**Throws:**

- Error if called during a request instead of at initialization
- Error if authentication is not set up

**Example:**

```ts
// At the top level of your module (initialization time)
const canViewAllOrders = authService.permission("ViewAll", "order");
const canCancel = authService.permission("Cancel", "order", ["admin", "support"]);

// Later, inside a handler
if (await canCancel(req.user)) {
  // proceed
}
```

#### `checkStaticAccessControl(user, action, accessControl)`

Checks a user's role(s) against a static access control configuration. Used internally by `authorize` and `permission`, but exposed for custom authorization logic.

**Parameters:**

- `user` (User): The user object, which must contain a `role` or `roles` field
- `action` (string): The action being performed
- `accessControl` (AccessControlConfig): The configuration to check against

**Returns:**

- boolean (true if the user is authorized)

**Throws:**

- Error if the user has neither a `role` nor a `roles` field

#### `checkDynamicAccessControl(userId, action, resource)`

Checks a user's permissions for an action and resource against the database (dynamic mode). Used internally by `authorize` and `permission`, but exposed for custom authorization logic.

**Parameters:**

- `userId` (string): The unique identifier of the user
- `action` (string): The action being performed
- `resource` (string): The resource being accessed

**Returns:**

- Promise resolving to boolean

## Custom Actions and Extended Authentication

The `AccessAction` type can be extended beyond the basic CRUD operations ("Create", "Update", "Delete", "View") to include custom actions specific to your application needs. This works in both static and dynamic authentication modes.

<Callout type="info">
When defining custom actions, note that the standard base actions ("Create", "Update", "Delete", "View") must use Pascal case (capital first letter). Your custom actions can use any naming convention, though we recommend maintaining consistency in your codebase.
</Callout>

**Example of custom actions:**

```ts
// Custom export functionality with specific access controls
router.get(
  "/api/reports/export",
  authService.authenticate,
  authService.handleAccessControl(
    "Export", // Custom action in Pascal case
    "report",
    ["Admin", "Analyst"] // accessControl
  ),
  exportReportController
);

// Custom bulk operation with specific permissions
router.post(
  "/api/users/bulk-invite",
  authService.authenticate,
  authService.handleAccessControl(
    "BulkInvite", // Custom action in Pascal case
    "user",
    ["Admin", "HR"] // accessControl
  ),
  bulkInviteController
);
```

<Callout type="idea">
For more detailed information on implementing authentication in custom routers, see the guide on [Adding Authentication to Custom Routers](/docs/core-concepts/routing/setup#adding-authentication-to-custom-routers).
</Callout>

## Properties

### `actionsPerResource`

A `Record<string, Set<string>>` tracking, per resource, every action registered through [`permission`](#permissionaction-resource-accesscontrol) or the deprecated `handleAccessControl`. Arkos reads it to expose the available actions through the `GET /api/auth-actions` endpoint, so frontend clients can discover what a user may do.

```ts
const actions = authService.actionsPerResource["order"];
// Set { "ViewAll", "Cancel", ... }
```

## Type Reference

This section provides reference information for the TypeScript types used with the auth service.

### `AccessAction`

Represents the possible actions that can be performed by a controller, including standard CRUD operations and custom actions.

```ts
export type AccessAction = "Create" | "Update" | "Delete" | "View" | string;
```

### `AccessControlRules`

Defines access control rules for different controller actions. Each key maps to an array of allowed role names, a wildcard, or a `DetailedAccessControlRule`.

```ts
export type AccessControlRules = {
  [key in AccessAction]: string[] | DetailedAccessControlRule | "*";
};
```

### `DetailedAccessControlRule`

A richer access control rule that carries metadata alongside the allowed roles. Used by `authorize` and by `permission` in static mode.

```ts
export type DetailedAccessControlRule = {
  roles?: string[] | "*";
  name?: string;
  description?: string;
  errorMessage?: string;
};
```

### `AuthenticationControlRules`

Specifies which actions require authentication.

```ts
export type AuthenticationControlRules = {
  [key in AccessAction]: boolean;
};
```

### `AuthenticationControlConfig`

Configuration for authentication control. Can be a boolean (applies to all actions) or specific rules per action.

```ts
export type AuthenticationControlConfig =
  | boolean
  | Partial<AuthenticationControlRules>;
```

### `AccessControlConfig`

Configuration for access control. Can be an array of roles (applies to all actions), a wildcard, or specific rules per action.

```ts
export type AccessControlConfig =
  | string[]
  | Partial<AccessControlRules>
  | "*";
```

### `AuthConfigs`

Configuration for authentication and access control.

```ts
export type AuthConfigs = {
  authenticationControl?: AuthenticationControlConfig;
  accessControl?: AccessControlConfig;
};
```

### `AuthJwtPayload`

Payload structure for JWT-based authentication, extending the standard `JwtPayload`.

```ts
export interface AuthJwtPayload extends JwtPayload {
  id?: number | string;
  [x: string]: any;
}
```

## Best Practices

1. **Use What Is Needed**: Try to avoid rewriting things that **Arkos** do behind the scenes unless you really now what you want to do.

2. **Custom Authentication Flows**: When implementing specialized authentication like SSO or multi-factor authentication, use the built-in authService methods as building blocks rather than reimplementing core logic.

3. **Security Context**: Always maintain the security context through the request pipeline. Avoid storing sensitive information in request objects that will be exposed to the client.

4. **Graceful Degradation**: When implementing optional authentication, ensure your application gracefully handles unauthenticated scenarios rather than failing completely.

5. **Role-Based Policies**: Use the access control handlers to create fine-grained permission policies based on roles and resource ownership rather than hardcoding permissions checks.

6. **Error Standardization**: Follow Arkos error handling patterns by using AppError with appropriate status codes to maintain consistent API responses for authentication failures.
